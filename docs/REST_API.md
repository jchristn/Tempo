# Tempo REST API

This document is the workflow reference for creating, managing, invoking, and monitoring Tempo data flows, steps, triggers, artifacts, and runs.

Tempo exposes a versioned REST API under `/v1.0`. Most management endpoints are tenant-scoped:

```text
/v1.0/tenants/{tenantId}/...
```

The public HTTP trigger endpoints are intentionally not tenant-scoped:

```text
/v1.0/triggers/http/{triggerId}
```

Use the trigger ID as a bearer capability unless the deployment places another gateway or authentication layer in front of public trigger routes.

## Base URL

Default local server:

```text
http://localhost:8901
```

Examples below use:

```text
BASE=http://localhost:8901
TENANT_ID=ten_example
TOKEN=...
```

Windows `cmd.exe` curl examples should call `curl.exe` to avoid the PowerShell alias:

```cmd
curl.exe -H "Authorization: Bearer %TOKEN%" "%BASE%/v1.0/api/health"
```

PowerShell examples can use:

```powershell
curl.exe -H "Authorization: Bearer $env:TOKEN" "$env:BASE/v1.0/api/health"
```

## Authentication

Management endpoints require an authenticated principal with permission to act on the requested tenant.

Supported authentication inputs:

| Header | Purpose |
| --- | --- |
| `Authorization: Bearer {token}` | Bearer token issued by `/v1.0/token` |
| `x-token: {token}` | Token header alternative |
| `x-api-key: {key}` | System admin API key |
| `x-access-key: {key}` and `x-secret-key: {secret}` | Credential pair authentication |
| `x-tenant-id: {tenantId}` | Optional tenant hint for credential authentication |
| `x-email` and `x-password` | Password-auth header flow |

Issue a token:

```http
POST /v1.0/token
Content-Type: application/json

{
  "tenantId": "ten_example",
  "email": "user@example.com",
  "password": "sha256-or-configured-password-value"
}
```

Validate the current token:

```http
GET /v1.0/token
Authorization: Bearer {token}
```

Read the authenticated principal:

```http
GET /v1.0/me
Authorization: Bearer {token}
```

Health check is pre-authentication:

```http
GET /v1.0/api/health
```

## Common Conventions

All JSON examples use camelCase property names.

Identifiers are generated by the server. New IDs use a resource prefix, a K-sortable component, and random entropy, with a maximum length of 32 characters.

| Resource | Prefix | Example shape |
| --- | --- | --- |
| Tenant | `ten_` | `ten_{ksort}_{random}` |
| Data flow | `flow_` | `flow_{ksort}_{random}` |
| Step | `step_` | `step_{ksort}_{random}` |
| Trigger | `trg_` | `trg_{ksort}_{random}` |
| Flow run | `run_` | `run_{ksort}_{random}` |
| Worker | `wrk_` | `wrk_{ksort}_{random}` |
| Worker session | `wse_` | `wse_{ksort}_{random}` |
| Run assignment | `ras_` | `ras_{ksort}_{random}` |
| Step run | `sru_` | `sru_{ksort}_{random}` |
| Artifact | `art_` | `art_{ksort}_{random}` |
| Artifact version | `arv_` | `arv_{ksort}_{random}` |

Do not build behavior by parsing IDs. Use prefixes for human auditing only.

Paged list endpoints accept:

| Query | Default | Purpose |
| --- | --- | --- |
| `pageNumber` | `1` | 1-based page number |
| `pageSize` | implementation default | Page size |
| `includeInactive` | `false` | Include inactive records |

List responses use an enumeration wrapper similar to:

```json
{
  "pageNumber": 1,
  "pageSize": 25,
  "totalCount": 3,
  "items": []
}
```

Errors are returned as JSON error responses with an HTTP status code. The message is meant for clients and operators; do not depend on exact punctuation or phrasing for control flow.

## Runtime Catalog

Before creating artifact-backed or host-backed steps, inspect runtime availability:

```http
GET /v1.0/runtimes
GET /v1.0/runtimes/{runtimeKey}
GET /v1.0/runtimes/external-execution
GET /v1.0/tenants/{tenantId}/runtimes
GET /v1.0/tenants/{tenantId}/runtimes/external-execution
POST /v1.0/tenants/{tenantId}/runtimes/validate
```

Known runtime keys:

| Runtime key | Use |
| --- | --- |
| `Builtin.Class` | Registered in-process class step |
| `Builtin.Method` | Registered in-process method step |
| `Builtin.Unknown` | Compatibility marker for unresolved legacy built-ins |
| `External.Rest` | Persisted REST step |
| `Legacy.InlineRest` | Read-path compatibility for older inline REST flow transitions |
| `Artifact.Process` | Runs a process from an artifact package |
| `Artifact.Python` | Runs a Python function from an artifact package |
| `Artifact.JavaScript` | Runs a JavaScript function from an artifact package |
| `Artifact.DotnetProcess` | Runs a .NET process from an artifact package |
| `Host.Executable` | Runs an operator allowlisted host executable |

Validate runtime configuration before saving complex steps:

```http
POST /v1.0/tenants/{tenantId}/runtimes/validate
Content-Type: application/json

{
  "runtimeKey": "Artifact.JavaScript",
  "config": {
    "runtimeKey": "Artifact.JavaScript",
    "artifactId": "art_example",
    "artifactVersion": "current",
    "entrypoint": "main",
    "module": "index.js",
    "function": "run"
  }
}
```

## Steps

A step is a reusable execution unit. Data flows refer to steps by `executionKey`, not by the step record ID. Keep `executionKey` stable; rename `name` for display changes.

### Step Endpoints

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/v1.0/tenants/{tenantId}/steps` | Create a persisted step |
| `POST` | `/v1.0/tenants/{tenantId}/steps/source` | Create an artifact-backed step from pasted source code |
| `GET` | `/v1.0/tenants/{tenantId}/steps` | List steps |
| `GET` | `/v1.0/tenants/{tenantId}/steps/{id}` | Read one step |
| `PUT` | `/v1.0/tenants/{tenantId}/steps/{id}` | Update one step |
| `DELETE` | `/v1.0/tenants/{tenantId}/steps/{id}` | Delete one step if unprotected and unused |
| `POST` | `/v1.0/tenants/{tenantId}/steps/bulk-delete` | Delete multiple unprotected and unused steps |
| `GET` | `/v1.0/steps/registered` | List built-in code registrations in the running process |

### Step Record Fields

| Field | Required | Notes |
| --- | --- | --- |
| `id` | server-generated | Prefix `step_` |
| `tenantId` | server-managed | Tenant owner |
| `executionKey` | yes | Tenant-scoped stable key used by flow transitions, max 255 chars |
| `name` | yes | Display name |
| `description` | no | User-facing description |
| `runtimeKey` | yes | One of the runtime keys above |
| `runtimeConfig` | yes | Typed config matching `runtimeKey` |
| `contractType` | no | Defaults to `Loose` |
| `inputSchema` | no | JSON schema string for input validation |
| `outputSchema` | no | JSON schema string for output validation |
| `validateInput` | no | Validate input before invoking the runtime |
| `validateOutput` | no | Validate output after runtime completion |
| `maxRuntimeMs` | no | `0` means no per-step timeout |
| `active` | no | Inactive steps should not be selected for new execution |
| `isProtected` | no | Protected steps cannot be deleted |
| `artifactId` / `artifactVersion` | server-maintained | Resolved for artifact-backed runtimes |
| `runtimeBindingState` / `runtimeBindingMessage` | server-maintained | Runtime reconciliation state |

### Create a REST Step

```http
POST /v1.0/tenants/{tenantId}/steps
Content-Type: application/json

{
  "executionKey": "example.call_weather_api",
  "name": "Call weather API",
  "description": "Calls an external REST service",
  "runtimeKey": "External.Rest",
  "runtimeConfig": {
    "runtimeKey": "External.Rest",
    "method": "POST",
    "url": "https://example.com/weather",
    "headers": {
      "Content-Type": "application/json"
    },
    "timeoutMs": 30000
  },
  "contractType": "Loose",
  "maxRuntimeMs": 45000,
  "active": true
}
```

The `runtimeConfig.runtimeKey` must match the top-level `runtimeKey`.

### Create a Built-In Method Step

Built-in steps are backed by code loaded into the Tempo.Server process. Use `/v1.0/steps/registered` to discover valid identifiers, types, methods, and signature hashes.

```http
GET /v1.0/steps/registered
```

```json
{
  "executionKey": "tempo.sample.builtin.method",
  "name": "Sample built-in method",
  "runtimeKey": "Builtin.Method",
  "runtimeConfig": {
    "runtimeKey": "Builtin.Method",
    "identifier": "tempo.sample.builtin.method",
    "declaringType": "Tempo.Server.Runtime.StartupSampleSteps",
    "methodName": "Echo",
    "assemblyName": "Tempo.Server",
    "assemblyVersion": "0.1.0",
    "signatureHash": "..."
  }
}
```

### Create a Step from Source

Use `/steps/source` when a user pastes a single Python, JavaScript, or C# file and wants Tempo to package it as an artifact-backed step.

Supported `language` values:

| Canonical | Accepted aliases |
| --- | --- |
| `Python` | `py` |
| `JavaScript` | `js`, `node`, `nodejs` |
| `CSharp` | `c#`, `cs`, `dotnet`, `.net` |

Python example:

```http
POST /v1.0/tenants/{tenantId}/steps/source
Content-Type: application/json

{
  "executionKey": "example.echo_python",
  "name": "Echo Python",
  "language": "Python",
  "fileName": "handler.py",
  "function": "run",
  "code": "def run(input):\n    return {\"ok\": True, \"input\": input}\n"
}
```

JavaScript example:

```json
{
  "executionKey": "example.echo_js",
  "name": "Echo JavaScript",
  "language": "JavaScript",
  "fileName": "handler.js",
  "function": "run",
  "code": "exports.run = async function(input) { return { ok: true, input }; };\n"
}
```

C# example:

```json
{
  "executionKey": "example.echo_csharp",
  "name": "Echo C#",
  "language": "CSharp",
  "fileName": "Handler.cs",
  "handlerType": "Tempo.UserSteps.Handler",
  "code": "using System.Threading;\nusing System.Threading.Tasks;\nusing Tempo.Protocol;\n\nnamespace Tempo.UserSteps;\n\npublic sealed class Handler : ITempoStepHandler\n{\n    public Task<StepResult> RunAsync(StepRequest request, CancellationToken token)\n    {\n        return Task.FromResult(TempoStepHost.Success(request, new { ok = true, input = request.Data }));\n    }\n}\n"
}
```

The response includes both the created `step` and the created `artifact`.

Important artifact-editing behavior:

| Language | Editing source files in the artifact affects execution? |
| --- | --- |
| Python | Yes, when the runtime executes the edited source in the current snapshot |
| JavaScript | Yes, when the runtime executes the edited source in the current snapshot |
| C# | Not by editing `.cs` source alone; the .NET runtime executes the packaged entrypoint assembly. Recreate the source step or upload a rebuilt package to change compiled behavior |

`External.Rest`:

```json

```

```json
  "environmentReferences": []
}
```

`Artifact.JavaScript`:

```json
{
  "runtimeKey": "Artifact.JavaScript",
  "artifactId": "art_example",
  "artifactVersion": "current",
  "entrypoint": "main",
  "module": "handler.js",
  "function": "run",
  "arguments": [],
  "environmentReferences": []
}
```

`Artifact.DotnetProcess`:

```json
{
  "runtimeKey": "Artifact.DotnetProcess",
  "artifactId": "art_example",
  "artifactVersion": "current",
  "entrypoint": "main",
  "arguments": [],
  "environmentReferences": []
}
```

`Artifact.Process`:

```json
{
  "runtimeKey": "Artifact.Process",
  "artifactId": "art_example",
  "artifactVersion": "current",
  "entrypoint": "main",
  "arguments": [],
  "environmentReferences": []
}
```

`Host.Executable`:

```json
{
  "runtimeKey": "Host.Executable",
  "allowListKey": "echo",
  "arguments": ["hello"]
}
```

For artifact-backed runtimes, `artifactId` is required. `artifactVersion` can be pinned to a label, or can use the mutable current snapshot when configured as `current` or omitted by the runtime plan. Pin versions when reproducibility matters.

`environmentReferences` contain environment variable names only, never `name=value` pairs.

### Update a Step

```http
PUT /v1.0/tenants/{tenantId}/steps/{stepId}
Content-Type: application/json

{
  "name": "Echo Python v2",
  "description": "Updated display metadata",
  "active": true,
  "isProtected": false
}
```

The update request is partial. Only supplied fields are applied. Changing `executionKey` changes how flows must refer to the step; do this only with a coordinated flow update.

### Delete a Step

```http
DELETE /v1.0/tenants/{tenantId}/steps/{stepId}
```

Deletion is blocked when:

| Condition | Reason |
| --- | --- |
| `isProtected` is `true` | Protected records are not deleted |
| Any data flow references the step `executionKey` | Deleting would break flow execution |

Prefer inactivation over deletion when preserving run history or staged rollout behavior matters.

## Artifacts

Artifacts store packages and editable files used by artifact-backed runtimes. Tempo treats artifacts as mutable. The dashboard and REST API can edit individual files and rebuild the current snapshot.

### Artifact Endpoints

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/v1.0/tenants/{tenantId}/artifacts` | Create artifact metadata |
| `GET` | `/v1.0/tenants/{tenantId}/artifacts` | List artifacts |
| `GET` | `/v1.0/tenants/{tenantId}/artifacts/{id}` | Read artifact metadata |
| `PUT` | `/v1.0/tenants/{tenantId}/artifacts/{id}` | Update artifact metadata |
| `DELETE` | `/v1.0/tenants/{tenantId}/artifacts/{id}` | Delete artifact if unprotected and unused |
| `GET` | `/v1.0/tenants/{tenantId}/artifacts/{id}/files` | List mutable files |
| `GET` | `/v1.0/tenants/{tenantId}/artifacts/{id}/files/content?path={path}` | Read one mutable file |
| `PUT` | `/v1.0/tenants/{tenantId}/artifacts/{id}/files/content?path={path}` | Create or replace one mutable file |
| `DELETE` | `/v1.0/tenants/{tenantId}/artifacts/{id}/files/content?path={path}` | Delete one mutable file |
| `POST` | `/v1.0/tenants/{tenantId}/artifacts/{id}/versions` | Upload a binary artifact version |
| `GET` | `/v1.0/tenants/{tenantId}/artifacts/{id}/versions` | List artifact versions |
| `GET` | `/v1.0/tenants/{tenantId}/artifacts/{id}/versions/{version}` | Read version metadata |
| `GET` | `/v1.0/tenants/{tenantId}/artifacts/{id}/versions/{version}/download` | Download version bytes |
| `DELETE` | `/v1.0/tenants/{tenantId}/artifacts/{id}/versions/{version}` | Delete version if unprotected and unused |

### Create Artifact Metadata

```http
POST /v1.0/tenants/{tenantId}/artifacts
Content-Type: application/json

{
  "name": "Order enrichment scripts",
  "description": "Python files used by order enrichment steps"
}
```

### Save an Artifact File

```http
PUT /v1.0/tenants/{tenantId}/artifacts/{artifactId}/files/content?path=handler.py
Content-Type: application/json

{
  "content": "def run(input):\n    return {\"ok\": True, \"input\": input}\n",
  "contentType": "text/x-python",
  "isBinary": false
}
```

Response:

```json
{
  "file": {
    "path": "handler.py",
    "contentType": "text/x-python",
    "isBinary": false,
    "byteLength": 62,
    "lastUpdateUtc": "2026-04-20T18:00:00.0000000Z"
  },
  "artifactVersion": {
    "id": "arv_example",
    "artifactId": "art_example",
    "version": "current",
    "sha256": "..."
  },
  "snapshotUpdated": true,
  "snapshotError": null
}
```

The query-string `path` wins if both query and body provide a path. Paths are artifact-relative. URL-encode nested paths:

```text
?path=src%2Fhandler.py
```

### Read an Artifact File

```http
GET /v1.0/tenants/{tenantId}/artifacts/{artifactId}/files/content?path=src%2Fhandler.py
```

Text files return JSON metadata and content. Binary files use base64 content when represented through JSON.

### Upload an Artifact Version

Upload raw package bytes. ZIP packages are common, but the route accepts raw binary content.

```http
POST /v1.0/tenants/{tenantId}/artifacts/{artifactId}/versions?version=1.0.0&originalFileName=package.zip&contentType=application/zip
Content-Type: application/zip

<binary bytes>
```

Optional query values:

| Query | Purpose |
| --- | --- |
| `version` | Version label. Use semantic labels, build labels, or `current` for mutable-current imports |
| `sha256` | Expected SHA-256 digest |
| `originalFileName` | Download filename metadata |
| `contentType` | Content type metadata |
| `manifestJson` | Manifest JSON if not embedded in the package |

When uploading a package with a valid manifest as version `current`, Tempo can import it into the mutable files table and rebuild the current snapshot.

### Artifact Manifest Notes

Artifact-backed runtimes use package manifests to resolve entrypoints, runtime keys, and executable files. Source-step creation writes the manifest automatically. Custom packages should include a manifest compatible with:

| Runtime | Required information |
| --- | --- |
| `Artifact.Process` | Runtime key and executable entrypoint |
| `Artifact.Python` | Runtime key, entrypoint/module, and function |
| `Artifact.JavaScript` | Runtime key, entrypoint/module, and function |
| `Artifact.DotnetProcess` | Runtime key and entrypoint assembly/process target |

### Delete Artifacts and Versions

Artifact deletion is blocked when protected or when any step references the artifact. Version deletion is blocked when protected or when any step references that artifact version.

Deletion is retention-aware: deleted versions can be marked for garbage collection rather than immediately removing blob bytes.

## Data Flows

A data flow connects step execution keys with transition rules. The output of one step becomes the input to the next selected step. The final step output becomes the flow run output.

### Data Flow Endpoints

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/v1.0/tenants/{tenantId}/flows` | Create a data flow |
| `GET` | `/v1.0/tenants/{tenantId}/flows` | List data flows |
| `GET` | `/v1.0/tenants/{tenantId}/flows/{id}` | Read one data flow |
| `PUT` | `/v1.0/tenants/{tenantId}/flows/{id}` | Update one data flow |
| `DELETE` | `/v1.0/tenants/{tenantId}/flows/{id}` | Delete one data flow if unprotected and unused |
| `POST` | `/v1.0/tenants/{tenantId}/flows/{id}/runs` | Enqueue a direct flow run |
| `POST` | `/v1.0/tenants/{tenantId}/flows/{id}/ensure-steps` | Create placeholder steps for missing transition keys |
| `POST` | `/v1.0/tenants/{tenantId}/flows/bulk-delete` | Delete multiple unprotected and unused flows |

### Data Flow Fields

| Field | Required | Notes |
| --- | --- | --- |
| `id` | server-generated | Prefix `flow_` |
| `tenantId` | server-managed or body-aligned | Tenant owner |
| `name` | yes | Display name |
| `description` | no | User-facing description |
| `triggerId` | no | Optional trigger associated with this flow |
| `startStepId` | yes | First execution key. Must exist in `transitions` |
| `routingHintLabel` | no | Worker-placement hint used when `engine.loadBalancingStrategy` is `LabelPinned` |
| `maxRuntimeMs` | no | Flow-level runtime budget. `0` means no flow timeout |
| `transitions` | yes | Map from execution key to transition definition |
| `active` | no | Active flag |
| `isProtected` | no | Protected flows cannot be deleted |

### Transition Fields

Transitions are keyed by step `executionKey`.

| Field | Purpose |
| --- | --- |
| `name` | Human-readable transition name |
| `onSuccess` | Next execution key when the current step returns success |
| `onFailure` | Next execution key when the current step returns failure |
| `onException` | Next execution key when the current step throws or times out |
| `maxTransitions` | Maximum number of times this transition can be visited |
| `stepType` | Legacy transition type hint |
| `rest` | Legacy inline REST configuration |

Use `null` for a terminal path.

### Create a Single-Step Flow

```http
POST /v1.0/tenants/{tenantId}/flows
Content-Type: application/json

{
  "name": "Echo flow",
  "description": "Returns the output from the echo step",
  "startStepId": "example.echo_python",
  "maxRuntimeMs": 30000,
  "transitions": {
    "example.echo_python": {
      "name": "Echo",
      "onSuccess": null,
      "onFailure": null,
      "onException": null,
      "maxTransitions": 1
    }
  },
  "active": true
}
```

### Create a Chained Flow

```json
{
```

### Ensure Placeholder Steps

```http
POST /v1.0/tenants/{tenantId}/flows/{flowId}/ensure-steps
```

This route scans transition keys and creates stub `Code` steps for missing keys. It is useful while sketching flows, but replace placeholders with real step runtime configuration before relying on execution.

### Enqueue a Direct Run

```http
POST /v1.0/tenants/{tenantId}/flows/{flowId}/runs
Content-Type: application/json

{
  "requestId": "optional-client-request-id",
  "data": {
    "value": "hello world"
  },
  "metadata": {
    "source": "api-client"
  }
}
```

Direct run enqueue returns a run record, usually with state `Queued`, and does not wait for completion:

```json
{
  "id": "run_example",
  "tenantId": "ten_example",
  "dataFlowId": "flow_example",
  "state": "Queued",
  "inputData": "{\"value\":\"hello world\"}",
  "createdUtc": "2026-04-20T18:00:00.0000000Z",
  "lastUpdateUtc": "2026-04-20T18:00:00.0000000Z"
}
```

Poll `/runs/{id}` and `/runs/{id}/steps` for completion details.

### Delete a Data Flow

```http
DELETE /v1.0/tenants/{tenantId}/flows/{flowId}
```

Deletion is blocked when:

| Condition | Reason |
| --- | --- |
| `isProtected` is `true` | Protected records are not deleted |
| Any trigger references the flow | Deleting would leave a trigger pointing at nothing |

## Triggers

A trigger invokes a data flow. Current public trigger execution is HTTP-based and supports `GET` and `POST` according to the trigger configuration.

### Trigger Endpoints

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/v1.0/tenants/{tenantId}/triggers` | Create a trigger |
| `GET` | `/v1.0/tenants/{tenantId}/triggers` | List triggers |
| `GET` | `/v1.0/tenants/{tenantId}/triggers/{id}` | Read one trigger |
| `PUT` | `/v1.0/tenants/{tenantId}/triggers/{id}` | Update one trigger |
| `DELETE` | `/v1.0/tenants/{tenantId}/triggers/{id}` | Delete one trigger if unprotected |
| `POST` | `/v1.0/tenants/{tenantId}/triggers/bulk-delete` | Delete multiple unprotected triggers |
| `GET` | `/v1.0/triggers/http/{id}` | Fire a public HTTP trigger with no request body |
| `POST` | `/v1.0/triggers/http/{id}` | Fire a public HTTP trigger with a request body |

### Trigger Fields

| Field | Required | Notes |
| --- | --- | --- |
| `id` | server-generated | Prefix `trg_` |
| `tenantId` | server-managed or body-aligned | Tenant owner |
| `name` | yes | Display name |
| `description` | no | User-facing description |
| `triggerType` | yes | Currently `Http` |
| `dataFlowId` | yes for invocation | Flow to enqueue |
| `configuration` | no | JSON string interpreted by trigger type |
| `active` | no | Inactive triggers cannot be fired |
| `isProtected` | no | Protected triggers cannot be deleted |

### HTTP Trigger Configuration

`configuration` is stored as a JSON string. For HTTP triggers:

```json
{
  "allowedMethods": ["POST"],
  "headers": {
    "Content-Type": "application/json"
  },
  "bodySchema": {
    "type": "object"
  }
}
```

If `allowedMethods` is missing or invalid, the server defaults to `["POST"]`.

Create a POST trigger:

```http
POST /v1.0/tenants/{tenantId}/triggers
Content-Type: application/json

{
  "name": "Echo HTTP trigger",
  "description": "Invokes the echo flow",
  "triggerType": "Http",
  "dataFlowId": "flow_example",
  "configuration": "{\"allowedMethods\":[\"POST\"],\"headers\":{\"Content-Type\":\"application/json\"}}",
  "active": true
}
```

Create a GET trigger:

```json
{
  "name": "Random double GET trigger",
  "triggerType": "Http",
  "dataFlowId": "flow_random_double",
  "configuration": "{\"allowedMethods\":[\"GET\"]}",
  "active": true
}
```

### Fire a Trigger

POST with JSON body:

```http
POST /v1.0/triggers/http/{triggerId}
Content-Type: application/json

{
  "value": "hello world"
}
```

GET with no body:

```http
GET /v1.0/triggers/http/{triggerId}
```

Unlike direct flow run enqueue, HTTP trigger invocation waits for the run to finish up to a bounded timeout. On success, the response body is the final flow output only:

```json
{
  "ok": true,
  "input": {
    "value": "hello world"
  }
}
```

Run metadata is returned in response headers:

| Header | Purpose |
| --- | --- |
| `x-tenant-id` | Tenant that owns the trigger and run |
| `x-worker-id` | Assigned worker ID or server pseudo-worker ID when available |
| `x-run-id` | Flow run ID |
| `x-dataflow-id` | Data flow ID |
| `x-trigger-id` | Trigger ID |
| `x-run-state` | Final or current run state |
| `x-run-created-utc` | Run enqueue time |
| `x-run-started-utc` | Run start time, when available |
| `x-run-completed-utc` | Run completion time, when available |
| `x-run-last-update-utc` | Last update time |
| `x-runtime-ms` | Runtime duration with up to two decimal places |
| `x-run-error` | Error text when available |
| `Access-Control-Expose-Headers` | Exposes the metadata headers to browsers |

Status behavior:

| Status | Meaning |
| --- | --- |
| `200` | Run completed successfully; response body is flow output |
| `202` | Run did not reach a terminal state before the wait budget; response body is current output if any |
| `404` | Trigger or associated flow was not found |
| `405` | HTTP method is not allowed by trigger configuration |
| `409` | Run was cancelled |
| `500` | Run failed or threw an exception |

The trigger wait budget defaults to 30000 ms. If the data flow has `maxRuntimeMs > 0`, the wait budget is `maxRuntimeMs + 5000`, clamped between 1000 ms and 600000 ms.

### Delete a Trigger

```http
DELETE /v1.0/tenants/{tenantId}/triggers/{triggerId}
```

Deletion is blocked when `isProtected` is true. Deleting a trigger does not delete its flow or historical runs.

## End-to-End: Source Step, Flow, Trigger, Run

1. Create a source step:

```http
POST /v1.0/tenants/{tenantId}/steps/source
Content-Type: application/json

{
  "executionKey": "demo.echo",
  "name": "Demo echo",
  "language": "JavaScript",
  "fileName": "handler.js",
  "function": "run",
  "code": "exports.run = async function(input) { return { ok: true, input }; };"
}
```

2. Create a flow using the step execution key:

```http
POST /v1.0/tenants/{tenantId}/flows
Content-Type: application/json

{
  "name": "Demo echo flow",
  "startStepId": "demo.echo",
  "transitions": {
    "demo.echo": {
      "name": "Echo",
      "onSuccess": null,
      "onFailure": null,
      "onException": null,
      "maxTransitions": 1
    }
  },
  "active": true
}
```

3. Create a POST trigger for the flow:

```http
POST /v1.0/tenants/{tenantId}/triggers
Content-Type: application/json

{
  "name": "Demo echo trigger",
  "triggerType": "Http",
  "dataFlowId": "flow_from_step_2",
  "configuration": "{\"allowedMethods\":[\"POST\"]}",
  "active": true
}
```

4. Invoke it:

```cmd
curl.exe -i -X POST "http://localhost:8901/v1.0/triggers/http/trg_from_step_3" -H "Content-Type: application/json" -d "{\"value\":\"hello world\"}"
```

Expected response body:

```json
{
  "ok": true,
  "input": {
    "value": "hello world"
  }
}
```

Expected response headers include:

```text
x-worker-id: wrk_...
x-run-id: run_...
x-dataflow-id: flow_...
x-trigger-id: trg_...
x-run-state: Succeeded
x-runtime-ms: 12.34
```

## OpenAPI

The server publishes OpenAPI metadata for route and schema discovery through Watson Webserver's OpenAPI support. Runtime configuration schemas use a discriminator-style `runtimeKey` plus concrete runtime config schema entries. Treat `runtimeConfig` as one of the concrete runtime config objects listed above.

Use the OpenAPI document for generated clients, but keep these workflow rules in mind:

| Rule | Reason |
| --- | --- |
| Flows reference steps by `executionKey` | Step record IDs are not used in transitions |
| HTTP trigger success body is flow output only | Run metadata lives in response headers |
| Direct flow run enqueue is asynchronous | Poll runs and step runs for final state |
| Artifact files are mutable | Saving files updates the current snapshot |
| Protected and referenced records cannot be deleted | Deletion guards preserve working flows and artifacts |

## Operational Checklist

Before exposing a flow through a trigger:

1. Confirm every transition key maps to an active step.
2. Validate every step runtime config.
3. For artifact-backed steps, confirm runtime availability and artifact version policy.
4. Set `maxRuntimeMs` on flows and process-backed steps.
5. Create a trigger with an explicit `allowedMethods` list.
6. Fire the trigger once and capture `x-run-id`, `x-runtime-ms`, and `/runs/{id}/steps`.
7. Protect production steps, flows, triggers, and artifacts from accidental deletion.

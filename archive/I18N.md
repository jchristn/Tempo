# Dashboard Internationalization Plan

## Status Legend
- [ ] Not started
- [-] In progress
- [x] Complete
- [!] Blocked / needs decision

## Objective
Make every dashboard-owned user-facing string, label, title, tooltip, placeholder, confirmation, chart label, empty state, accessibility label, and login/auth surface render in the user's selected language.

This plan is intentionally broader than "translate a few labels". The current dashboard mixes:
- hardcoded English UI copy
- browser-default number/date formatting
- raw backend/server-authored text
- generated setup-wizard sample names and code strings
- CSS/layout assumptions that fit English better than CJK, Romance, or RTL languages

The result needs to scale to any number of locales without re-architecting again after the first few languages.

## Scope
In scope:
- `dashboard/index.html`
- `dashboard/src/main.jsx`
- `dashboard/src/App.jsx`
- `dashboard/src/context/AuthContext.jsx`
- `dashboard/src/components/*`
- `dashboard/src/views/*`
- `dashboard/src/utils/*`
- `dashboard/src/index.css`
- `dashboard/src/App.css`
- dashboard tests under `dashboard/src/**/*.test.*`
- any server-authored text shown inside the dashboard UX, where the dashboard currently renders raw backend output

Out of scope:
- translating database IDs, runtime keys, enum wire values, JSON property names, API paths, or code identifiers used as protocol data
- changing business rules unrelated to localization
- translating built dashboard output under `dashboard/dist/` directly

## Source Locale And Target Locales
Source locale:
- `en`

Requested first wave:
- `en` - English
- `es` - Spanish
- `zh-Hans` - Mandarin Chinese, Simplified
- `yue-Hant-HK` - Cantonese, Traditional Chinese (Hong Kong)
- `ja` - Japanese
- `de` - German
- `fr` - French
- `it` - Italian

Recommended additions for a serious first pass:
- `zh-Hant-TW` - Mandarin Chinese, Traditional
- `ko` - Korean
- `pt-BR` - Portuguese (Brazil)
- `ar` - Arabic, so RTL support is designed now instead of bolted on later

Important note about "Kanji":
- Kanji is not a standalone language or locale.
- Treat the requested "Kanji" requirement as a Japanese script coverage requirement under `ja`.
- If product wants the selector to literally include the word "Kanji", implement it as an alias label that maps to `ja`, not as a separate locale.

## Non-Negotiable Rules
- Every new user-visible string must come from the i18n layer.
- English text must not be used as translation keys.
- Backend wire values must stay stable and untranslated; only their display labels change.
- Formatters must receive an explicit locale and must not rely on browser-default locale implicitly.
- The login page must have a language selector before authentication.
- The selected language must persist across reloads and survive logout/login transitions.
- `document.documentElement.lang` and `document.documentElement.dir` must update when locale changes.
- The plan must support lazy-loading more locales later without changing component architecture.

## Recommended Technical Direction
Use `i18next` with `react-i18next` and ICU message support.

Recommended packages:
- `i18next`
- `react-i18next`
- `i18next-icu`
- `i18next-browser-languagedetector`

Why this stack:
- works well with React component trees and route-based namespaces
- supports pluralization, interpolation, and selection logic cleanly
- scales to many locales
- allows lazy-loaded resource bundles
- works well with pseudo-locales

Do not implement ad hoc translation maps inside components.

## Current High-Risk Patterns To Eliminate
- Direct English literals in JSX, helper functions, alerts, and error fallbacks
- `toLocaleString()` / `toLocaleDateString()` / `toLocaleTimeString()` without an explicit locale
- hardcoded `Yes`, `No`, `Any`, `Clear`, `Delete`, `Save`, `Cancel`, `(none)`, `(empty)`, `(terminate)`, `Loading...`, `Copied!`, `records`, `items`, and similar repeated UI strings
- `join(', ')` for localized lists instead of `Intl.ListFormat`
- raw enum values rendered directly as user-visible text
- raw backend error messages rendered directly without code-based localization strategy
- route/view tests that only pass because English copy is hardcoded
